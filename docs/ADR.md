# Architecture Decision Records

## 철학
개인용 자동화 도구. 확실하지 않은 페이지 구조는 추측하지 않고 실제 HTML을 받아 근거 기반으로 대응한다. "똑똑해 보이는" 최적화보다 단순하고 안전한 해법을 우선한다 — 복잡한 해법이 항상 나은 것은 아니라는 게 실제로 확인된 교훈이다.

---

### ADR-001: Playwright `.inner_text()` 등에는 항상 짧은 명시적 timeout을 준다
**결정**: 모든 텍스트 읽기 호출에 `_safe_inner_text()` 공용 헬퍼(짧은 timeout + fallback)를 강제한다.
**이유**: 정확히 일치하는 검색결과는 목록이 잠깐 떴다가 상세페이지로 자동 이동하는데, 그 사라지는 요소에서 텍스트를 읽으려다 Playwright 기본 30000ms 타임아웃까지 걸리는 심각한 hang이 있었다.
**트레이드오프**: 아주 드물게 느린 렌더링에서 빈 문자열(fallback)을 반환할 수 있음 — 재시도 로직으로 보완.

### ADR-002: 검색결과/예약대상 레이싱에 `asyncio.wait`+`task.cancel()`을 쓰지 않는다
**결정**: 여러 시그널(직접매치 vs 목록등장)을 기다릴 때 `asyncio.wait(..., return_when=FIRST_COMPLETED)` 대신 짧은 간격(`0.15s`) 폴링 루프를 쓴다.
**이유**: task 취소 시도가 Playwright 내부 상태와 맞물려 오히려 32초 지연을 유발하는 회귀를 일으켰다. 되돌리고 단순 폴링으로 교체함.
**트레이드오프**: 폴링 간격만큼의 지연(최대 0.15초)이 이론상 남지만, hang 위험 제거가 훨씬 중요.

### ADR-003: `target_name`(담당자/서비스/룸 등) 파싱은 업종에 종속시키지 않는다
**결정**: Claude tool schema의 `target_name` 설명을 "담당자, 룸, 서비스, 메뉴, 코스 등 업종 불문하고 무엇이든"으로 범용화한다.
**이유**: 처음엔 디자이너 이름 전용, 다음엔 병원 서비스 전용으로 좁혔다가 두 번 다 실제 사용 중 다른 업종에서 실패해 되돌렸다. 목표 자체가 "업종 무관하게 동작"이므로 스키마도 업종 비종속이어야 한다.
**트레이드오프**: 프롬프트가 다소 추상적이라 LLM이 가끔 엉뚱한 값을 넣을 수 있음 — `_pick_index_by_name`의 fuzzy match로 흡수.

### ADR-004: 멀티 유저/탭별 캐싱 확장은 지금 하지 않는다
**결정**: 업체·항목별로 탭을 미리 여러 개 띄워 캐싱하는 최적화안을 채택하지 않는다.
**이유**: 지금은 개인 단일 사용자 도구이고, 이 최적화는 향후 여러 사용자가 동시에 쓰는 구조로 갈 때 오히려 맞지 않는(스케일 안 되는) 방향이라 사용자가 명시적으로 반려함.
**트레이드오프**: 같은 세션 내 후속 질문 재사용(entry_iframe 유지)만으로 현재 체감 성능은 충분히 확보.

### ADR-005: 시간 슬롯 "결과 없음"과 "마크업 인식 실패"를 별도 상태로 분리한다
**결정**: `get_available_times_from_page()`가 빈 리스트만 반환하던 것을 `(available_times, status)`로 바꾸고, 신형/구형 시간 버튼 셀렉터 둘 다 후보를 하나도 못 찾은 경우를 `"unknown_markup"`이라는 별도 status로 구분한다. 이 상태가 되면 `_save_debug_artifacts()`가 그 순간의 HTML/스크린샷을 로컬 `debug/`(gitignore 처리)에 자동 저장하고, `find_earliest_available()`은 나머지 날짜를 계속 순회하지 않고 즉시 멈춘다.
**이유**: 기존엔 "이 날짜는 마감"과 "셀렉터가 아예 안 맞음(=사이트 마크업이 바뀜)"이 똑같이 빈 리스트로 보여서 구분이 안 됐다. 이러면 실제로는 마크업이 깨졌는데 "한동안 마감이었나 보다"로 오인하고 넘어갈 위험이 있고, 문제를 알아챈 시점에는 이미 그 페이지 상태가 사라져서 재현하려면 다시 개발자도구를 열어야 했다.
**트레이드오프**: 시간 슬롯 관련 함수(`get_available_times_from_page`/`find_earliest_available`/`check_specific_day`)의 반환 형태가 모두 튜플로 바뀌어 호출부(`query_place`, `main.py`의 레거시 메뉴)도 같이 수정해야 했다 — 하지만 "깨진 걸 늦게 알아채는" 위험을 없애는 게 더 중요하다고 판단.

### ADR-006: 장소 추천의 "요즘 뜨는 곳" 신호는 인스타그램이 아니라 네이버 리뷰 작성일 분포로 근사한다
**결정**: 추천 기능에서 "요즘 화제"를 인스타그램 트렌드/해시태그 스크래핑으로 구하지 않는다. 대신 이미 스크래핑 중인 네이버 리뷰의 작성일을 이용해 "최신 리뷰 10~20개 중 최근 30일 이내 비율"을 화제도 근사치로 쓴다.
**이유**: Instagram(Meta)은 지금까지 겪은 네이버 관련 약관/차단 리스크보다 훨씬 강한 안티스크래핑·법적 대응 전례가 있고, 애초에 "지역별 트렌드 장소" 조회를 지원하는 공식 API도 없다. 반면 리뷰 작성일은 네이버 안에서 이미 확보 가능한 데이터라 별도 시계열 수집 인프라(매일 스냅샷 저장 등) 없이도 콜드스타트 문제 없이 바로 계산할 수 있다.
**트레이드오프**: 진짜 SNS 바이럴 신호(공유수·언급량 급증)를 반영하진 못하고 "최근 방문객 반응"만 근사한다 — 하지만 리스크 대비 실익이 훨씬 크다고 판단.

### ADR-007: ~~장소 추천 랭킹에서 거리는 점수가 아니라 필터로 쓴다~~ (ADR-009로 대체됨)
**결정**: 추천 스코어링에 거리를 가중치로 섞지 않고, "반경 N km 이내"로 후보를 먼저 거른 뒤 그 안에서만 품질/트렌드로 랭킹한다.
**이유**: "500m 더 가까움"과 "평점 0.1 더 높음"을 하나의 숫자로 비교하려면 임의의 가중치를 정해야 하는데, 그 가중치 자체가 계속 애매한 논쟁거리가 된다. 거리를 필터로 분리하면 그 저울질이 아예 필요 없어진다.
**트레이드오프**: 반경을 약간만 벗어난, 아주 훌륭한 곳을 놓칠 수 있다 — 반경 기본값(2km)을 조정 가능하게 열어둠으로써 보완.
**대체 사유**: "반경의 기준점"을 사용자의 실제 위치로 잘못 가정하고 있었다(이 시스템은 사용자 위치 정보가 없음 — 기준은 질문에 언급된 지역명이어야 함). 이 버그를 계기로 거리 포함 전체 판단을 ADR-009로 넘김.

### ADR-008: ~~리뷰 적은 후보는 "검증된" 랭킹과 분리해 "신상" 트랙으로 따로 보여준다~~ (ADR-009로 대체됨)
**결정**: 베이지안 보정 평점(리뷰수가 적을수록 후보군 평균 쪽으로 당겨지는 방식)만 쓰지 않고, 리뷰수가 후보군 중앙값(median_reviews) 미만이면서 평점 ≥ 4.3, 최근 리뷰 비율 ≥ 80%인 후보는 "검증된" 순위표에서 빼서 "주목할 신상"으로 별도 표시한다. median_reviews는 검색마다(업종·지역 다르게) 그 자리에서 계산해 절대 기준(예: "리뷰 15개 이상") 없이 식당·카페·미용실·병원 등에 동일한 로직이 적용되게 한다.
**이유**: 베이지안 보정은 "리뷰 적음"을 전부 "신뢰 낮음 → 감점"으로 처리하는데, 최근에 문을 열어 아직 리뷰는 적지만 실제로 훌륭한 곳까지 같이 억눌러버리는 부작용이 있다. 하나의 점수로 뭉개는 대신 불확실성을 구조적으로 드러내는 쪽(두 트랙으로 분리)이, 사용자에게 "확실한 곳"과 "아직 검증 안 됐지만 반응 좋은 곳"을 있는 그대로 전달할 수 있어 더 정직하다.
**트레이드오프**: 응답이 한 줄로 안 끝나고 두 그룹으로 나뉘어 약간 길어진다 — 대신 신빙성 문제를 회피하지 않고 사용자 판단에 맡길 수 있다.
**대체 사유**: "신상" 판정 기준(4.3점, 80%)이 고정 임계치라 예외가 생길 때마다 코드를 계속 손봐야 했다(거리 기준점 버그가 그 예). 이런 임계치를 코드에 하드코딩하는 대신 Claude의 판단 원칙으로 옮기는 게 낫다고 판단해 ADR-009로 통합.

### ADR-009: 장소 추천의 랭킹/판단은 수식이 아니라 Claude tool-use에 맡긴다
**결정**: 베이지안 보정 공식, 고정 임계치(4.3점/80%/2km 등)로 추천 순위를 결정론적으로 계산하던 접근(ADR-007, ADR-008)을 버리고, 코드는 사실 수집(후보 목록, 평점/리뷰수/좌표, 최근 리뷰 날짜 샘플)까지만 하고 실제 "무엇을 추천할지" 판단은 `parse_natural_query()`와 동일한 패턴(Claude tool-use)으로 넘긴다. 판단 원칙(리뷰 적음을 숨기지 않기, 업종별 상대적 판단, 리뷰 이벤트성 몰림 의심, 거리는 질문에 언급된 지역 기준, 검증됨/신상 구분, 이유 명시)은 코드가 아니라 `docs/PRD.md`의 "장소 추천 알고리즘"에 문서화한다.
**이유**: "좋은 장소란 무엇인가"는 본질적으로 사람의 판단이 필요한 문제라, 수식/임계치로 모든 경우의 수(신상 가게, 리뷰 이벤트, 거리 기준점 등)를 미리 못박으려 할수록 예외가 끝없이 늘어났다(ADR-007의 반경 기준점 버그가 대표적 사례). 이미 자연어 파싱에 쓰고 있는 Claude tool-use 패턴을 재사용하면, 새로운 예외가 나올 때마다 코드를 고치는 대신 원칙 문서 한 줄을 고치면 되므로 유지보수 부담이 줄어든다.
**트레이드오프**: 같은 데이터를 넣어도 매번 결과가 완전히 결정론적으로 재현되진 않고, "왜 이 순서인지"를 수학적으로는 설명할 수 없다(대신 Claude가 각 추천에 이유를 붙여 설명 가능성을 확보한다). API 호출이 한 번 더 늘어난다.

### ADR-010: 장소 추천 후보 데이터는 로컬 JSON 파일에 "지역+업종" 키로 캐시한다 (TTL 24시간)
**결정**: 추천에 쓰는 후보 사실 데이터(평점/리뷰수/좌표, 최근 리뷰 샘플)를 매 질문마다 라이브로 다시 긁지 않고, `(지역, 업종)`을 키로 로컬 캐시 파일(예: `recommend_cache.json`, 로컬 전용·gitignore)에 저장해 24시간 동안 재사용한다.
**이유**: 예약 가능 시간과 달리 평점/리뷰수 같은 사실은 하루이틀 사이에 거의 안 바뀐다. 이 데이터는 사용자별이 아니라 "지역+업종" 조합에만 의존하는 객관적 사실이라, 예약 세션 캐싱(ADR-004, 사용자별이라 공유 불가)과 달리 여러 사용자가 같은 조합을 물어봐도 캐시를 그대로 공유할 수 있다 — 사용자가 늘어도 네이버에 나가는 실제 요청 수는 사용자 수가 아니라 "물어보는 지역+업종 조합의 다양성"에만 비례해, 약관/차단 리스크 관점에서도 유리하다.
**트레이드오프**: 지금은 개인용 단일 프로세스라 파일 하나로 충분하지만, 멀티 유저로 확장하면 동시 쓰기 충돌(파일 손상) 문제가 생겨 SQLite/Redis 같은 동시성 지원 저장소로 교체가 필요하다. 또한 같은 키를 동시에 여러 요청이 처음 조회하면 캐시 스탬피드(중복 라이브 스크래핑)가 생길 수 있는데, 이것도 지금은 신경 쓰지 않고 서비스화 시점에 락 메커니즘으로 보완한다. 아울러 캐시로 데이터를 여러 사용자에게 재배포하는 것 자체가 "개인 조회"와는 다른 카테고리의 약관/법적 리스크를 만들 수 있다는 점은 별도로 인지하고 있어야 한다.
