# Architecture Decision Records

## 철학
개인용 자동화 도구. 확실하지 않은 페이지 구조는 추측하지 않고 실제 HTML을 받아 근거 기반으로 대응한다. "똑똑해 보이는" 최적화보다 단순하고 안전한 해법을 우선한다 — 복잡한 해법이 항상 나은 것은 아니라는 게 실제로 확인된 교훈이다.

---

### ADR-001: Playwright `.inner_text()` 등에는 항상 짧은 명시적 timeout을 준다
**결정**: 모든 텍스트 읽기 호출에 `_safe_inner_text()` 공용 헬퍼(짧은 timeout + fallback)를 강제한다.
**이유**: 정확히 일치하는 검색결과는 목록이 잠깐 떴다가 상세페이지로 자동 이동하는데, 그 사라지는 요소에서 텍스트를 읽으려다 Playwright 기본 30000ms 타임아웃까지 걸리는 심각한 hang이 있었다.
**트레이드오프**: 아주 드물게 느린 렌더링에서 빈 문자열(fallback)을 반환할 수 있음 — 재시도 로직으로 보완.

### ADR-002: 검색결과/예약대상 레이싱에 `asyncio.wait`+`task.cancel()`을 쓰지 않는다
**결정**: 여러 시그널(직접매치 vs 목록등장)을 기다릴 때 `asyncio.wait(..., return_when=FIRST_COMPLETED)` 대신 짧은 간격(`0.15s`) 폴링 루프를 쓴다.
**이유**: task 취소 시도가 Playwright 내부 상태와 맞물려 오히려 32초 지연을 유발하는 회귀를 일으켰다. 되돌리고 단순 폴링으로 교체함.
**트레이드오프**: 폴링 간격만큼의 지연(최대 0.15초)이 이론상 남지만, hang 위험 제거가 훨씬 중요.

### ADR-003: `target_name`(담당자/서비스/룸 등) 파싱은 업종에 종속시키지 않는다
**결정**: Claude tool schema의 `target_name` 설명을 "담당자, 룸, 서비스, 메뉴, 코스 등 업종 불문하고 무엇이든"으로 범용화한다.
**이유**: 처음엔 디자이너 이름 전용, 다음엔 병원 서비스 전용으로 좁혔다가 두 번 다 실제 사용 중 다른 업종에서 실패해 되돌렸다. 목표 자체가 "업종 무관하게 동작"이므로 스키마도 업종 비종속이어야 한다.
**트레이드오프**: 프롬프트가 다소 추상적이라 LLM이 가끔 엉뚱한 값을 넣을 수 있음 — `_pick_index_by_name`의 fuzzy match로 흡수.

### ADR-004: 멀티 유저/탭별 캐싱 확장은 지금 하지 않는다
**결정**: 업체·항목별로 탭을 미리 여러 개 띄워 캐싱하는 최적화안을 채택하지 않는다.
**이유**: 지금은 개인 단일 사용자 도구이고, 이 최적화는 향후 여러 사용자가 동시에 쓰는 구조로 갈 때 오히려 맞지 않는(스케일 안 되는) 방향이라 사용자가 명시적으로 반려함.
**트레이드오프**: 같은 세션 내 후속 질문 재사용(entry_iframe 유지)만으로 현재 체감 성능은 충분히 확보.
