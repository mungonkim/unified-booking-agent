# PRD: 통합 예약 에이전트

## 목표
네이버 예약, 캐치테이블 등 여러 예약 플랫폼에 흩어진 임의의 업종(식당/미용실/병원·클리닉/사진관 등) 예약 정보를 사용자가 자연어로 물어보면 통합해서 확인해주고, 결제가 없는 예약이면 자동으로 예약까지 진행하며, 결제가 필요한 경우에만 사용자가 직접 결제하도록 안내한다. 추가로 사용자가 원하는 조건에 맞는 장소도 추천한다.

## 사용자
개인 사용자 1인 (본인). 여러 업체를 그때그때 물어보며 사용.

## 현재 구현 범위 (네이버 예약 조회만)
1. 자연어 질의 입력 → 장소명/담당자(디자이너·서비스·룸 등)/인원/조회모드(가장 빠른 날짜 vs 특정 일자)를 추출
2. 네이버 지도 검색 → 검색결과 다건이면 자동/대화형으로 소거 → 예약 페이지 진입
3. 업종별로 다른 중간 선택 화면(디자이너/서비스카드/룸 등) 자동 대응
4. 신형/구형 캘린더 마크업 모두 대응, 날짜 선택 후 가용 시간 슬롯 조회
5. 인원 선택이 필요한 업체(식당 등)만 인원을 되물음
6. 같은 장소/같은 항목에 대한 후속 질문은 세션(엔트리 iframe) 재사용으로 재검색 생략
7. (레거시) `--menu` 플래그로 기존 대화형 CLI 메뉴도 계속 지원

## 앞으로 만들 핵심 기능 (README 체크리스트 참고)
1. 네이버 예약 — 결제 없는 예약은 실제 예약 신청까지 자동 진행
2. 결제 필요 여부 판단 → 필요하면 자동 진행하지 않고 사용자에게 결제 링크/화면을 넘겨 직접 결제하게 함
3. 캐치테이블 지원 — 검색~조회~(결제 없으면) 예약까지 네이버와 동등한 수준으로
4. 네이버/캐치테이블 등을 하나의 공통 인터페이스로 묶는 플랫폼 어댑터 계층 (신규 플랫폼 추가가 쉬워야 함)
5. 조건(업종/지역/시간대 등) 기반 장소 추천 — 상세 설계는 아래 "장소 추천 알고리즘" 참고

## 장소 추천 알고리즘 (설계 확정, 구현 전)
사용자가 "홍대 근처 파스타 맛집 추천해줘" 처럼 업종+지역으로 물으면, 아래 방식으로 후보를 골라 자연어로 답한다. 업종(식당/카페/미용실/병원/사진관 등)에 상관없이 동일한 로직으로 동작해야 한다(하드코딩 금지 원칙, CLAUDE.md 참고).

**구조: 사실 수집(코드) + 판단(Claude)을 분리한다.** "좋은 장소란 무엇인가"는 본질적으로 사람의 판단이 필요한 문제라, 베이지안 보정·고정 임계치 같은 수식으로 모든 경우의 수를 미리 못 박으려다 보면 예외가 끝없이 늘어난다(반경 기준점이 사용자 위치인지 지역명인지, 신상 가게를 어떻게 봐줄지, 업종별 리뷰수 정상범위 등). 대신 `parse_natural_query()`와 같은 방식으로, 코드는 판단에 필요한 사실만 모으고 실제 랭킹/추천 판단은 Claude tool-use에 맡긴다.

1. **후보 수집 (코드)**: 지역+업종 키워드로 네이버 지도 검색 → 후보 N개의 이름/카테고리/평점/리뷰수/좌표·주소 수집. `(지역, 업종)` 키로 로컬 캐시(24시간 TTL, ADR-010)를 먼저 확인하고, 없거나 만료됐을 때만 실제로 접속해서 가져온다.
2. **최근 리뷰 샘플 수집 (코드)**: 상위 후보(예: 8개)에 한해서만 개별 페이지에서 최신 리뷰 10~20개의 작성일(+가능하면 별점)을 추가로 수집 — 전체 후보를 다 깊게 스크래핑하지 않도록 저렴한 필터 → 정밀 조회 2단계 구조. 이 데이터도 같은 캐시에 함께 저장한다.
3. **판단은 Claude에게 (tool-use)**: 위 사실들과 함께 아래 원칙을 프롬프트로 전달해 최종 추천 목록을 구조화된 형태로 받는다.
   - 리뷰 수가 적으면 그 평점의 확신도가 낮다는 걸 숨기지 말고 그대로 알려줄 것 (예: "리뷰 5개뿐이라 아직 검증되지 않았지만…")
   - 업종마다 "리뷰 많다"의 정상 범위가 다르다 — 이번 후보군 안에서 상대적으로 판단할 것 (식당은 수백 개가 흔하고 미용실·병원은 한 자릿수도 정상)
   - 리뷰가 짧은 기간에 급증했다고 무조건 좋은 신호로 보지 말 것 — 리뷰 이벤트(별점 남기면 서비스 제공 등)로 인한 몰림일 수 있으니, 자연스러운 입소문인지 의심해볼 것
   - 거리 판단은 질문에 언급된 지역(예: "홍대") 기준이지, 사용자의 실제 위치가 아님 (이 시스템은 사용자의 실제 위치 정보를 가지고 있지 않음)
   - 확실히 검증된 곳과 아직 검증 중이지만 주목할 만한 곳(리뷰는 적지만 반응이 좋은 신상)을 섞지 말고 구분해서 제시할 것
   - 추천마다 짧고 구체적인 이유를 붙일 것 (사용자가 "왜 이 순서야?"라고 물으면 답할 수 있을 정도로)
4. **응답**: "검증된 곳" 상위 3~5개 + (있으면) "주목할 신상"을 구분해서 이유와 함께 자연어로 제공

**의도적으로 하지 않는 것**: 인스타그램 등 SNS 트렌드 직접 스크래핑(약관/차단 리스크가 네이버보다 훨씬 큼) — "요즘 화제"는 네이버 리뷰 자체의 작성일 분포로 근사한다. 정밀한 수식(베이지안 공식, 고정 임계치)으로 랭킹을 결정론적으로 재현 가능하게 만드는 것도 하지 않는다 — 그 대신 Claude의 판단 원칙을 문서(이 항목)로 관리해 필요하면 원칙 자체를 수정한다.

## MVP 제외 사항
- 멀티 유저 동시 서비스화 (API 서버, 동시 세션 격리) — 개인용 단일 세션으로 충분한 동안은 보류
- 업체별 캐시를 다중 탭으로 미리 열어두는 최적화 — 확장성 문제로 명시적으로 보류
- 네이버/캐치테이블 이외의 추가 플랫폼 — 우선 두 플랫폼부터
